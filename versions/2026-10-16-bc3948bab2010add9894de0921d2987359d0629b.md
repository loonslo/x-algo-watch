### 视频轮播新增语义向量去重，但默认关闭；其他改动主要是可观测性与训练配置扩展

本次最明确的机制变化是为视频轮播候选增加基于帖子多模态 embedding 的可选去重：先通过 Manhattan 获取 v8_search_1 向量，再把阈值和开关传给视频选择逻辑。开关默认关闭，因此仅凭源码不能认定线上已改变候选或曝光。另有 PopularPosts 来源标识、可见性过滤延迟指标，以及 Phoenix 训练/数据配置的可配置项扩展，整体更偏向配套和观测，而非直接改写召回来源或排序模型。

### 算法机制可能改在哪里

- **视频轮播语义去重**：以前“视频轮播候选没有从帖子 embedding 获得的额外去重信号；已有作者去重和 semantic ID 去重参数仍由视频轮播选择逻辑使用。”；现在“新增 EnableVideoCarouselEmbeddingDedupe 和 VideoCarouselEmbeddingDedupeThreshold。开关打开且视频轮播启用时，VideoEmbeddingHydrator 为轮播视频获取 v8_search_1、维度为 1024 的 embedding；VideoCarouselFilter 将开关和阈值传入 select_videos。”。（E1、E3、E11、E17、E18、E19）
- **embedding 获取失败时降级**：以前“视频轮播没有新增 embedding 外部依赖。”；现在“Manhattan 客户端初始化失败时改用 Noop 客户端；批量读取失败、反序列化失败或维度不符合时返回空结果，因此没有 embedding 的候选只能沿用其余去重信号。”。（E12、E14、E18、E19）
- **PopularPosts 来源标识**：以前“PopularPostsSource 使用 ForYouPhoenixRetrieval 作为 served type。”；现在“改为 ForYouPopularPosts，使共享热门帖子来源在 served type 上与其他 Phoenix 检索来源区分。”。（E16）
- **可见性过滤可观测性**：以前“调用方请求统计按 caller、rpc、deadline、outcome 计数；客户端延迟使用 observe 指标。”；现在“服务端新增成功请求的按调用方延迟直方图 vf_request_latency_by_caller_ms，并移除 deadline 维度；客户端延迟改为 observe_vm 指标。”。（E5、E9、E10）
- **可见性过滤结果语义与测试覆盖**：以前“Evaluation::Complete 只携带 verdict，golden corpus 主要验证 verdict。”；现在“Complete 允许携带额外字段；测试新增 best-effort 节点失败与 must-have 节点失败的区分，要求 must-have 失败时结果进入 Partial，但最终 verdict 保持预期。”。（E1、E6）
- **Phoenix 训练配置扩展**：以前“数据构造和 trainer 配置未显式传递 output_vocab_size、站点停留时间历史拼接、行 embedding 等选项。”；现在“增加 output_vocab_size、concat_history_web_conv_time_on_site、use_row_emb、row_emb_recv_factor 等配置传递；具体是否改变线上模型取决于对应配置值。”。（E7、E8）

### 对推荐结果的推测

#### 当视频轮播和 embedding 去重开关同时在线启用，且 select_videos 会依据 embedding 相似度与 0.72 阈值执行去重时，视觉或语义高度相似的轮播视频中可能有一批被移除，从而改变轮播内部候选构成。

- 把握：中等（针对机制推断，不代表已部署）。
- 为什么这样推测：新 hydrator 把每个轮播视频的原始帖子 embedding 写入候选，filter 再把开关和阈值传给 select_videos；这比仅增加日志更直接地接入候选选择链路。
- 成立条件：线上参数覆盖将 EnableVideoCarouselEmbeddingDedupe 开启；Manhattan 客户端和相应 embedding 可用；select_videos 的实际实现确实使用传入阈值。
- 对创作者意味着什么：可能优先影响主题、画面或表达方式相近的轮播视频作者；主题不同的作者可能较少受影响。是否获得更多展示不能从本版本推出。
- 另一种解释：阈值可能只用于排序、平滑或软惩罚，而非硬删除；当前证据没有提供 select_videos 的实现。
- 如何验证：对照 home-mixer/util/video_carousel.rs 中 select_videos 的比较方式、阈值方向和删除逻辑，并检查线上参数快照及候选移除指标。
- 依据：E1、E3、E11、E17、E18

#### 启用新去重后，相似内容之间的曝光可能从“同轮播中的重复项”转向较少重复的候选，但总体候选来源构成和普通内容排序信号未必改变。

- 把握：中等（针对机制推断，不代表已部署）。
- 为什么这样推测：embedding 只写入 PostCandidate 的 video_embedding，并仅在视频轮播选择器中作为新增可选参数使用；证据没有显示它进入 PhoenixScorer、RankingScorer 或通用预评分过滤。
- 成立条件：改动只影响视频轮播请求，且线上开关开启；相似度规则确实能移除候选。
- 对创作者意味着什么：反复发布近似画面或近似主题的作者可能少占轮播位置；差异化视频可能获得更多轮播内位置，但这不是曝光量或收益保证。
- 另一种解释：如果相似度不足、embedding 缺失或 select_videos 不采用该阈值，候选和曝光会保持原状。
- 如何验证：检查启用前后视频轮播候选数、每轮视频数、重复主题占比，并核对普通视频请求的过滤与打分路径。
- 依据：E2、E11、E15、E17

#### Phoenix 的新增训练配置更像能力接线：只有相应 mparams 开启后，才可能改变模型输入历史、输出词表或嵌入通信方式。

- 把握：较高（针对机制推断，不代表已部署）。
- 为什么这样推测：配置代码只是把新字段传入数据、dispatcher 和 trainer；例如 concat_history_web_conv_time_on_site 与 use_row_emb 的读取默认值均为 False。
- 成立条件：具体训练作业的 mparams 显式启用相应选项；仅合并代码不会自动改变已训练或已部署模型。
- 对创作者意味着什么：若历史站点停留时间或行 embedding 真正进入训练，行为可能间接影响个性化排序，但当前证据不足以判断哪些创作者或内容类型受益。
- 另一种解释：这些字段可能仅为兼容性或未来实验准备，当前训练配置可能完全没有使用。
- 如何验证：检查实际训练配置中的 mparams、模型导出物版本和推理服务加载的模型版本，区分训练侧与线上 serving 侧。
- 依据：E7、E8
