### 推荐流新增“零收藏内容”作者分流，并强化视频轮播去重

本次核心不是统一改排序分数，而是在打分前改变部分候选的准入：新增 ZeroFavCodivertFilter，按观众开关和作者实验分组决定纯零收藏召回是否保留；同时默认打开视频轮播的作者与语义向量去重，并新增可关闭的互动者信息补全。总体会调整候选来源构成和重复内容处理；是否改变个性化历史或主排序信号，现有证据不足。

### 算法机制可能改在哪里

- **零收藏候选的作者级分流**：以前“没有 ZeroFavCodivertFilter；纯 ForYouPhoenixRetrievalZeroFav 候选不会因该实验规则被单独过滤。”；现在“过滤器接入 Phoenix 候选管线并位于打分前。观众开关启用后，仅 treatment 作者的纯零收藏候选被保留，control 与 unbucketed 作者的此类候选被移除；混合来源候选不受影响。”。（E1、E4、E16、E20、E21、E26）
- **视频轮播重复内容处理**：以前“EnableVideoCarouselAuthorDedupe 与 EnableVideoCarouselEmbeddingDedupe 默认均为 false，VideoCarouselSemanticIdDedupeLevels 为 0。”；现在“两个去重开关默认改为 true，语义 ID 去重层级默认值改为 3；视频嵌入补全仅在轮播启用且向量去重开启时获取嵌入，选择阶段会把作者去重、语义层级和向量阈值传入选片逻辑。”。（E1、E18、E19、E24）
- **互动者信息补全**：以前“证据中未显示 PostEngagersHydrator 的接入。”；现在“新增候选补全器：开关启用或流量属于 shadow traffic 时，为候选获取 PostEngagers；按原始帖子 ID 缓存，缓存 TTL 为 60 秒、容量为 500_000，存在缓存帖子时跳过。默认开关为 false。”。（E1、E17、E22、E23、E26）
- **Phoenix 离线特征读取适配**：以前“Parquet 迭代器没有 id-list sidecar 的选择、严格缺失检查和来源统计路径。”；现在“可优先读取 sidecar 中的 id-list 特征，也可回退原生列；严格模式下缺少 sidecar 会报错，并记录 sidecar、native、none 三类来源。RustParquetDataset 配置 sidecar 时明确不支持。”。（E8、E27、E29、E31）

### 对推荐结果的推测

#### 在 ZeroFavCodivert 观众开关开启的请求中，treatment 作者能获得单独的纯零收藏内容通道，而 control 作者的同类内容会被提前挡掉，因此即使最终排序公式不变，两组作者也可能获得不同的候选来源构成。

- 把握：较高（针对机制推断，不代表已部署）。
- 为什么这样推测：过滤器在候选管线中先执行；它只保留 treatment 作者的纯 ForYouPhoenixRetrievalZeroFav 候选，control 和 unbucketed 均被移除，且还按作者分组记录候选数与唯一作者数。
- 成立条件：ViewerZeroFavCodivertIsTreatment 为 true；候选的主 served_type 和全部 retrieval_sources 都是 ForYouPhoenixRetrievalZeroFav；作者规则正确落入对应桶。
- 对创作者意味着什么：主要影响被分入 treatment、control 或 unbucketed 的作者，尤其是内容主要通过纯零收藏召回触达的作者；这不保证 treatment 作者获得更多总曝光，只能确认其纯零收藏候选获准进入后续流程。
- 另一种解释：线上开关未开启、作者规则未覆盖相关作者，或候选实际混有其他召回来源时，两组作者看到的差异会很小或不存在。
- 如何验证：对照线上参数值、作者规则覆盖范围，并按 author_bucket 比较过滤前后 ZeroFav 候选数、唯一作者数及最终展示构成。
- 依据：E4、E16、E21、E26

#### 默认开启作者去重和嵌入去重后，视频轮播更可能减少同一作者或语义相近视频连续占位，重复视频的曝光位置会被其他候选替代。

- 把握：中等（针对机制推断，不代表已部署）。
- 为什么这样推测：两个去重开关默认值改为 true，语义 ID 去重层级改为 3；轮播选择函数收到这些配置，同时嵌入补全器会在向量去重开启时运行。
- 成立条件：请求进入 video carousel 模式，且轮播候选带有执行作者、语义 ID 和嵌入去重所需的字段；被去重候选仍有其他候选可替代。
- 对创作者意味着什么：同作者批量发布、相近题材或模板化视频较多的创作者，可能少占轮播中的相邻或重复位置；差异内容或缺少近重复候选的创作者相对不受影响。
- 另一种解释：去重可能只改变轮播内部顺序或候选选择，并不改变普通信息流；若候选缺少对应字段，效果也可能有限。
- 如何验证：比较开关组合下轮播选片结果，重点检查同作者连续项、嵌入相近项和语义 ID 相同项的保留数量及其最终位置。
- 依据：E1、E19、E24

#### PostEngagers 补全目前更像为后续排序或实验准备的数据入口，不能仅凭其接入就断定主排序已改变。

- 把握：中等（针对机制推断，不代表已部署）。
- 为什么这样推测：新组件只负责把 post_engagers 写入候选并带缓存；默认开关为 false，shadow traffic 也会触发，但证据包未展示 PhoenixScorer 或其他排序器读取该字段的调用。
- 成立条件：若下游排序器确实读取 post_engagers，则启用开关或 shadow traffic 后可能改变排序；若仅用于观测或实验，则不会直接改变排序。
- 对创作者意味着什么：在尚未确认消费链前，不能认定任何创作者会因该补全获得排序优势；最多只能说开启后具备使用互动者信息的条件。
- 另一种解释：该字段可能只被旁路实验、指标或后续未展示组件消费。
- 如何验证：检查 home-mixer/scorers/phoenix_scorer.rs 及所有 post_engagers 读取点，并对比启用前后最终分数。
- 依据：E17、E22、E23、E26

### 复核分歧

- 关于 ZeroFavCodivertFilter 所处阶段的疑问与现有证据及分析正文矛盾。项目架构明确把 filters 描述为 pre-scoring filters，且分析自己的 changes 也已断言该过滤器“打分前”；因此不应再称“当前证据未给出 filters 与 scorer 的完整执行顺序”。若仍要保留问题，应改为核对过滤器相对于具体候选来源、hydrator 和其他 filter 的精确执行顺序及失败时序，而不是把打分前后列为未知。（E2、E16、E26）
- 视频轮播去重假设没有明确纳入线上参数覆盖这一必要条件。两个布尔开关和语义层级虽然代码默认值改为 true/3，但证据明确说明公开默认值可能与线上设置不同、部署未知；实际效果要求线上值仍启用相应开关，不能仅由源码默认值推出。verify 中比较“开关组合”是离线验证手段，线上效果还应先核对当前部署值。（E1、E19、E24）
