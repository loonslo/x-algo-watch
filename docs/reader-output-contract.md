# 线上版本解读输出协议 v2（算法版本更新公告）

当前本地待上线的两个机制试点以文末“新机制试点主链”为准；前半部分保留旧链 v2/v3 协议，供已有审计与非试点路径解释，不能当作新试点的结论或质量验收。

默认读者是普通创作者与运营。技术用户按需展开页面底部的分析；需要追溯的人再展开证据与研究记录。这套规则用于后续线上模型起草、复核和自动排版，不要求每次再准备人工改写稿。

## 用户影响优先（v3）

先完成源码机制研究，再筛选有用户因果链的变化，最后写普通中文正文。读者包括刷推荐、看通知、搜索和发布内容的普通用户。正文按用户场景与影响排序，不按模块、枚举或参数排序。每项写清同一场景“以前 → 现在的代码如何处理 → 因此你可能感受到什么”，并保留关键条件与边界。

代码重构、内部实验采样、时间戳及尚未找到用户因果链的发现进入技术分析，不强迫逐项写进 reader。对普通用户没有足够证据时，允许 impacts 为空，直接说明暂不能确认体验变化，不编造影响或行动建议。正文所有字段禁止代码标识和研究过程术语；机器可检查格式与标识，具体场景是否有依据仍由三个审核角色核对。

用户页顺序：公告标题与一次线上状态说明；更新重点；你可能感受到的变化（每项前后对比、用户影响、成立条件）；现在怎么做；折叠技术分析与研究附录。审核通过时，候选历史和技术状态表放研究附录；未通过时首先展示真实状态、已核实的检测范围和缺口，不套用公告标题或体验对比。技术专页仍可直接展开研究。两页来自同一研究。

证据准备将长规则名单压缩为完整、可解析的精确新增/移除差集与前后数量，避免直接截断 JSON。当前改动及直接关联参数的实现优先，无关的已有组件不应挤掉实际差异。缺失旧行为不等于以前无限制，新增定义不等于新功能部署。三角色既核事实，也核对普通读者能否复述具体变化；不得要求每项内部改动进入用户正文，或用无限补免责声明代替解释。

## 模型输出字段

旧 reader 缺少 before/after 仍可作为原研究审计读取，不冒充通过新规则；线上新起草和修订必须满足新用户影响契约。

完整机器协议为 [schemas/version-research-v2.json](../schemas/version-research-v2.json)，由 `research_schema()` 生成。线上起草与复核的系统提示都会追加同一份完整协议；版本指纹包含各角色提示词、协议、请求路由和所需复核轮数，规则改变后不会把旧关卡当成已通过新关卡。

根对象只允许 `item_id`、`title`、`summary`、`reader`、`changes`、`hypotheses`、`no_hypothesis_reason`、`questions`。其中技术字段供底部分析使用，用户区从 `reader` 生成，不把技术摘要再复制一遍。

如果本地校验只发现标题/四问的术语、单字段长度、合计长度错误，或影响条目/术语解释中明确定位的代码标识及研究过程词，纠错请求使用程序导出的窄协议：仅返回 `reader_patch`，只含本次指定的用户字段（列表问题仅返回 impacts.序号.字段 或 terms.序号.字段 对应的字符串，程序原位替换，禁止替换整个列表或证据编号）。程序以安全扫描后的上一稿为基础合并，禁止修改其他字段或技术分析，再执行完整机器协议、全部证据校验和所有审核角色。包含数字、来源或技术事实错误时不走此捷径，仍进行整稿修订。原始补丁、合并稿、目标字段和调用审计均保存，失败次数与预算不重置；定点修补不等于审核通过。

| reader 字段 | 责任 |
| --- | --- |
| title | 普通中文标题，至多 80 字符 |
| what_changed | 改了什么，至多 200 字符 |
| who | 哪些读者或内容可能涉及，至多 160 字符 |
| when | 是否核实上线、关键默认状态、实验及请求条件，至多 220 字符 |
| online_status | 固定为 `unverified`；公开源码输入不能证明实际部署 |
| action | 是否有足够依据调整策略、现在如何处理，至多 160 字符 |
| impacts | 至多 4 项，可为空；每项只有 heading、before、after、effect、conditions、limits、evidence_refs；heading 为用户场景，before/after 比较同一场景，effect 说明用户感知 |
| terms | 至多 5 项必要解释；每项只有 term、meaning、evidence_refs |
| evidence_refs | 摘要依据，必须为本次证据包中实际存在的编号 |

根对象及各嵌套对象不接受额外字段。技术变量、Phoenix、VMRanker、“水合”和 kill switch 不进入任何用户正文字段；含义未核验的标签不能擅自解释成色情、擦边或其他类别。涉及关注关系时须核对实际赋值，不能把“关注关系之外”写成“X 平台以外”。

## 状态字面值规范化

当 reader.online_status 为 unverified，且 reader.when 出现精确的 online_status 为/固定为/:/= unverified 字面表达时，程序仅将该表达转换为“线上状态尚未核实”。原始响应原样保存，调用记录 normalizations 标明转换位置；其他代码标识、肯定部署断言、数字与机制结论不转换，之后仍执行全部校验和三角色审核。此规则不改变允许的事实或结论；旧的合格稿不含被替换的机器表达，可继续复用，原研究与历史不清空。

## 自动执行与失败分支

1. 检测器整理本次版本的源码证据；模型只能把其中内容当作数据。
2. 起草模型按协议返回 JSON，必须包含 reader。程序检查精确字段、长度、上线状态枚举、数字、名字、路径、证据编号和部署承诺。
3. 第一次校验失败，携具体错误自动重试一次；仍失败则标需人工，不生成可发布的用户正文。
4. 起草后执行三轮单独的模型复核，均读取同一协议、原始证据与同一稿件，不读取其他复核者的裁决：原有综合复核；新增源码事实与重要遗漏核对；新增机制推断与非技术读者理解核对。第三轮重点检查通俗化有无丢失关键条件、影响对象和行动边界。阅读层问题使用 `field=reader`。
5. 三个角色必须全部同意；任一角色有实质问题就合并异议并更新问题清单，依据原始证据修订后重新执行全部三个角色，即使稿件相同也不沿用上一候选裁决。默认最多 5 个候选，即初稿加 4 次修订；连续两次可识别的无进展或达到本批上限时暂停，保留稿件和明确恢复条件。已知问题同步修正 reader、标题、技术断言，不用多数票抵消异议。证据不足可收窄、撤回推断或明确未知，之后仍须全部审核同意。仍有分歧时用户正文待修订，原稿仅留在审计记录。
6. 通过后，程序固定排成上述四层，并把证据编号转换为可点击链接。新版本无需 `editorial/` 文件即可发布阅读页；正式 digest 仍须所有者确认。

2026-10-29 按用户指定，所有角色固定使用 `google/gemma-4-26b-a4b-it:free`，配置显式开启 `allow_same_model`。请求保留 JSON 输出要求；记录请求和实际响应型号，没有返回时明确为未知。这是同型号的三个审核角色，不能宣称异模型独立复核，也不能保证没有语义错误。旧 `openrouter/free` 调用仍留在审计，全部计入当日共享预算。

Gemma 端点支持 JSON 输出但不支持服务端 JSON Schema 强制约束，使用 `response_format=json_object` 及 `require_parameters`，关闭提供方故障切换。完整研究协议随请求发送，返回后仍执行全部本地结构、字段、引用与证据校验；三轮复核继续使用精确 agree/issues 协议。历史免费自动路由的严格 schema 传输保持兼容。模型选择参与调用键及研究指纹，新模型不复用旧路由的稿件、裁决或失败缓存。能力依据见 [OpenRouter 模型端点](https://openrouter.ai/api/v1/models/google/gemma-4-26b-a4b-it:free/endpoints)及[模型说明](https://openrouter.ai/google/gemma-4-26b-a4b-it:free)。

免费整版本起草设置 max_tokens=12,000、reasoning.max_tokens=3,000；审核设置 max_tokens=24,000、reasoning.effort=low，为完整裁决保留空间（实际提供方曾将 3,000 推理预算映射为超过 12,000，导致审核截断）；提供方可能映射或忽略推理设置，实际计数仍以安全审计为准。输出达到 length 边界视为未完成，不能使用部分 JSON，也不计入格式无效次数。请求失败、安全扫描命中和正文校验失败分别诊断，只记录固定类别、阶段和 HTTP 状态，不记录敏感原文或未知异常消息。CLI 与导入的循环共用 models.Deferred，避免把可恢复请求失败误报为安全拦截。

每个候选通常需要 4 次调用（起草或修订加三个角色审核），5 个候选全部执行且无重试时为 20 次。`max_candidate_versions` 默认 5（允许 2–10），`stagnation_limit` 默认 2（允许 1–5）。每阶段格式无效最多纠错一次；接口失败不增加候选号，但所有尝试计入每日 1,000 次共享预算，按 UTC 日期计数，不因路由、恢复或上限变化清零。单阶段累计三次接口失败后等待显式恢复，防止无限自动重试。

额度不足、连接延期或主动运行达到 20 分钟时保留已完成阶段，下次现有定时任务或手动工作流从缺少阶段继续；不另建调度器，不承诺故障期间的确切续跑时间。格式两次无效、接口失败三次、修订上限或停滞会显示等待人工处理，而非通过或任务完成。处理后，在 Check upstream algorithm 填写单个 `research_commit` 并勾选 `resume_iterations`，或者在只读 Review one version sample 填写对应提交并勾选同名选项；不勾选不会重启暂停的批次。本地等价参数为 drafting 的 `--resume`，须明确一个版本。恢复保留全部历史，开启新的候选批次；规则/上下文改变会产生新的输入或协议指纹，旧研究仍留审计。

`version_research.iteration` 保存同源证据摘要、候选序号、每版完整稿件和裁决、问题编号及状态、本批起点、恢复次数、具体暂停原因和下一步。调用缓存包含候选号及各阶段恢复代次；显式恢复失败阶段也复用其他已完成阶段。发布端检查历史、问题清单与最终裁决一致，不能修改 ready 标记绕过审核。问题按相同字段、证据及规范化问题文字生成稳定编号；改写后的同义问题不保证能识别，最终仍有候选上限。`not_repeated` 仅表示本版未再提出，不证明原质疑成立或已人工解决；只有本版全部审核通过后才标 `rechecked`，仍非人工确认。纯措辞偏好不应进入阻断意见，所有真实异议均保留，不自动投票删除。

公开两页和目录显示候选进度及恢复条件；最新研究决定当前展示状态；新稿未完成时用户页展示状态，旧研究仅作历史审计，不继续作为本轮正文。完整候选存于追加研究记录，不把所有历史原文塞进 Issue，避免超出评论长度。所有者本地预览还可检查上一候选和问题清单；尚无完整候选时只显示进度。未完成全部审核不能发布新正文，正式 digest 仍须人工确认。历史已通过稿保留当时复核方式，不冒充经过新增核对。

程序能约束结构与证据边界，不能单靠字段完整证明所有语义正确；事实遗漏、关键默认状态与标签解释仍须由各核对角色依据实际提供的源码判断。上下文未提供的内容只能记为证据缺口，不能假装通读了整个项目。

## 旧稿迁移

本次为已有 9 份研究准备了绑定具体 research_id、item_id 的阅读稿；3 份旧研究的分歧落实到改写内容，原模型输出不改写。其中最新版本补读的源码用 R 编号，与原模型 E 编号分开。迁移稿没有冒充新模型复核通过或所有者确认。

旧稿只在绑定的原研究仍作为阅读来源时生效。后续新研究返回合格 reader 后自动采用新模型结果，旧改写不会覆盖它。若新研究尚未完成，用户页、首页和目录统一显示最新状态；旧研究及迁移稿保留在审计中，不能覆盖新失败。

`readability_compatible_profiles` 只允许复用旧版本中已同意的机制研究，避免仅因阅读层改版重复调用 6 份已完成研究；不豁免旧分歧稿、失败稿或不同证据输入。后续生成不依赖迁移清单中另有人手写文案。

## 发布状态边界（2026-10-28）

首页速览、目录和用户页共用 publication_status，区分排队、处理中、证据不足、复核分歧、失败暂停、审核通过；检查未完成优先显示红色。证据不足仅用于有明确证据判定的状态，不能从接口失败或审核分歧自动猜测。当前审核事件协议尚未增加独立的证据不足裁决，待第二阶段接入。

必须有当前候选三个角色的完整同意裁决、空问题列表及一致的汇总结果，才能展示模型正文。旧迁移 reader 没有新增三角色审核，不能用作通过门槛的替代。正式 digest 仍经所有者确认；旧速报确认不能确认新研究。未通过时只写材料不足以支持据此调整策略，不推断变化无影响或主要是内部维护。

## 独立机制协议开发边界（2026-10-28 集成前历史记录）

分任务证据及独立机制判断的开发协议见 schemas/mechanism-research-v1.json，由 mechanisms.mechanism_schema() 导出。它先记录精确片段、前后行为、调用条件、反证与未知，输出 mechanisms_prepared 而非可发布 reader。C 编号通过版本、文件和稳定机制键绑定。同一版本补证得到新 plan_id，不能改写旧证据快照。

以上为集成前记录。本节不修改旧审计所使用的阅读协议，也不表示历史稿已经通过新关卡；最新本地集成进度见下节和 acceptance-integrated-research.md。

## 新机制试点主链（2026-10-28 集成）

config/watch.yaml 将 mechanisms-v1 限定在两个试点提交，mechanism_pilot_only 暂不研究其他历史模型队列。旧审计及 E 协议不改写；新链的 mechanism-review-v1.json 和 reader-research-v1.json 分别由 mechanism_reviews.review_schema()、reader_pipeline.reader_schema() 导出，角色请求使用同一精确协议。试点未准备新任务快照时拒绝退回旧起草流程。

每个任务先独立研究，再由综合机制、事实遗漏、推断理解三个角色分别核对同一原稿；仅提供本角色旧问题，不泄露其他角色裁决。问题绑定稳定 C 编号、JSON 字段路径、问题键和类别。缺证据先停止改稿，由下一次检测读取 Git 并加入新快照；证据变化继承原问题、候选号和全批边界，不清空预算。表达修订只允许改指定表达，所有修订重跑三关。原文、每版差异、处理理由、回退均保留；模型自己声明已关闭不代表通过。

共享架构和纯引用窗口标记 supporting_context，只支撑技术理解，不当作本次用户变化。每个变化文件另有当前处理结果：已研究、仅检测、缺少上下文或排除及理由；准备快照里的 not_researched 不会被改写成模型已研究。

全部机制任务获准后，从冻结判断选择读者重点，每批结论都须记录筛选去向，不再由固定文件窗口决定遗漏。编辑阶段只接收冻结判断及边界，不重做源码研究。每个文字字段绑定 C 编号；最多三个场景，旧行为未知时 before 为空且不排前后表格，无充分建议时明确材料不足。词表只解释正文用词。读者稿仍重新经过三个角色，同意不能用多数票替代。

发布端重验计划、逐任务裁决、筛选去向、读者依赖及全部读者裁决的一致性。只有 ready、全部机制及读者复核通过时展示正文；正式 digest 仍须所有者确认。请求发出前先保存 started 占用，响应后原子替换当前输出；中断意图也计入预算。新链审计按文件存储，检查记录仍是进度唯一来源。工作流会在失败后保存已有审计产物，不能把请求中断当成任务完成。

共享预算现已本地接入两个模型工作流：读取同仓库 main 的全部相关运行及重跑尝试，只补调用编号与日期，不能导入旧结论。新旧链每次网络请求前写独立账本，失败后也上传。账本或完整性无法核实则停止新请求，首页、目录和版本页统一显示“暂停调用（共享预算尚未核实）”；核对恢复后清除这一阻塞，研究仍从原阶段继续。详见 acceptance-shared-call-budget.md。

超大补证采用完整行分块 → 紧凑源码事实及三审 → 分层归并及三审 → 原机制及三审。每个子结论都必须有处理结果，反证、未知和 mock 用途不能在归并时消失；模型摘要不是源码，引文由程序从精确片段还原。原机制结论命名空间和候选边界保持，发布端重新核验全部依赖证明。分块及归并不进入用户变化池。协议见 schemas/context-research-v1.json，验收见 acceptance-context-consolidation.md。

此段描述本地实现及模拟验证，尚无新增真实模型质量验收或部署事实。归并的实际语义质量、新增预算工作流的远程核对及失败恢复尚未执行，详见 acceptance-integrated-research.md。
