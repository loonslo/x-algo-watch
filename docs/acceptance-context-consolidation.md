# 超大补证拆分与归并验收

维护及验收日期：2026-10-28。Windows / Python 3.14.0。本轮完成本地集成、模拟传输及真实 Git 对象回放，尚未调用新模型、推送或部署。

## 需求、模块与取舍

旧 enrich_plan 在必要补证超过 85,000 字符时停止，不能解决确实需要多份源码的问题。现在保留原机制任务和结论命名空间，将超大补证转成有依赖关系的分块及归并任务。小补证仍直接加入任务；直接源码超过 60,000 字符时拆分，为归并结果保留空间。

context_tasks.py 负责完整行分块、两两归并、紧凑事实协议、依赖验证及真实引文视图。pipeline_context.py 只读 Git 对象准备不可变快照；子任务补证变化会重新绑定上层任务和文件账本，保留旧任务别名与旧快照。mechanism_pipeline.py 按拓扑执行全部节点及三角色审核；reader_pipeline.py 和 pipeline_views.py 从相同依赖证明重建冻结判断。

流程是：完整补证窗口 → 每块源码事实研究及三审 → 分层归并及三审 → 原机制任务及三审 → 读者稿及三审。分块和归并仅能输出源码事实、反证或不足判断，不能输出机制假设或用户影响；读者筛选只接受原变化任务，不能把背景研究包装成版本变化。

- 每块至多 24,000 字符，只在完整行之间拆分，前后版本分别保留真实行号和用途。单行无法容纳时明确失败，旧快照不变，不按字符伪造完整行。
- 每份补证报告至多四项、整体不超过 6,000 字符，聚焦原问题。两份报告进入下一层；每个子结论及子任务总结果都形成 D- 区段，必须逐项说明采用、不相关或不足。反证、未知和 mock 用途不能为缩短而删除，是否语义正确仍由三个角色核对。
- 归并输入同时提供已核对的判断及程序还原的具体源码引文。模型报告不当作源码；新引用来自子任务精确片段，保留原路径、提交、行号及来源指针。每层只暴露实际引文，完整源码保留在叶子快照中。
- 原机制 C 编号的命名空间保持不变；每个分块/归并有独立身份，避免不同层的同名判断冲突。任务别名和跨快照候选边界沿用现有恢复协议，新增材料不重新获得五次候选机会。
- 起草可接收原问题清单；审核角色只接收自己的旧问题，共用原判断及新材料，不读取其他审核角色裁决。所有层都执行原三关、接口/格式失败边界、日预算和显式恢复规则。
- 发布端逐层复核子任务三关、每版依赖状态、源码引文视图摘要及调用实际视图摘要。缺子裁决、改摘要、改来源或删除依赖均不能靠 ready 标记绕过。
- 单次模型视图按序列化 JSON 限制为 120,000 字符；归并仍不足以容纳、问题仍过宽或报告不合格时保持不足/暂停，不截断后继续发布。分层处理消除了原始大窗口的固定停止，不承诺任意问题都能自动压缩且没有语义损失。

协议导出为 schemas/context-research-v1.json；起草提示为 prompts/context-analysis-v1.md。流程指纹已包含新提示和紧凑协议，旧审计不冒充新流程通过。

模拟传输验证了：

1. 先完成各层三审再运行原机制；归并异议立即回到 Git 补证，不能进入读者稿。
2. 反证出现在最后一块时，经过多层仍进入原判断；mock 不因归并变成生产事实，被否定判断不能进入用户场景。
3. 预算中断只补缺少阶段；最终原机制和读者三关全部通过才能本地展示正文，正式 digest 不自动生成。
4. 新的超大补证快照承接原候选号 1→2、原 C 编号和处理理由，不清空历史；审核者仅收到自己的旧问题。
5. 删除依赖、修改视图摘要、遗漏 D- 子结论、非法紧凑报告和超长单行被拒绝；检查进度不受影响。

随后在最新 main 基线的独立本地候选中完整回归为 421 passed、零跳过（518.68 秒）；最后文件账本透传补证缺口、早期执行器请求前记账等边界在候选相关检查中为 54 passed、2 deselected（109.54 秒）。详见 release-candidate-research-pipeline.md。文件账本包含子任务的缺证据状态与审计位置，不能由上层“已研究”遮蔽。

这些是控制和证据流转验证，不是免费路由语义质量验收。真实模型的完整性、归并是否丢条件、两个样例的内容对比及创作者可读性仍须实际核对。只有这些通过后才扩展历史研究。
