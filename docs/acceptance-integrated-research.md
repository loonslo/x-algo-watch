# 分任务机制研究主链集成验收

维护日期：2026-10-28。环境：Windows / Python 3.14.0。本文记录本地代码与验证，不代表已推送、上线、调用真实模型或通过读者质量验收。

## 已接通的实际路径

主链为 detect → 不可变分任务快照 → 独立机制起草 → 每任务三个审核角色 → 按问题补证/修订 → 冻结结论筛选 → 读者稿 → 读者稿三个审核角色 → 发布端重新验证 → 状态页/正文/技术页。旧研究及旧 E 协议保留原审计，新试点用 C 结论及精确字段依赖。

- pipeline_context 将全部变化文件、分块前后源码、两侧有界引用及用途标记接入检测产物。新计划按文件保存，manifest 最后写入，不再争抢旧 16 文件窗口。只在两个试点运行，显式解除 mechanism_pilot_only 后才将新链扩展至其他提交；试点缺新快照时拒绝回退旧模型流程。
- 每个机制任务独立起草，再由综合机制、事实遗漏、推断理解分别审核；全部同意才能进入编辑。共享架构和纯引用是 supporting_context，不能冒充本次用户变化。每个变化文件有已研究、仅检测、缺少上下文或排除及理由，准备快照仍保留 not_researched 的原始状态。
- 问题按 C 编号、具体字段、类别、稳定问题键定位。缺证据立即停止改稿，下一次检测按精确版本和行号读取 Git，再生成新快照。跨快照保留旧问题、处理理由、历史引用及候选号，不重新获得五次机会。表达修订限制在指定字段；替换旧机制键来躲避问题会被拒绝。处理理由并不等于关闭，所有修订仍重跑三关；重新出现的问题记录为回退。
- 冻结判断分批筛选，每条结论记录去向，不静默截掉后面的文件。编辑只读已研究判断及边界，生成最多三个场景，每个文字字段绑定 C 结论。旧行为未知时不排前后表格；没有充分用户建议时明确不足；术语只解释正文用词。读者稿再经过三角色，发布端检查完整任务裁决、筛选覆盖、依赖及正文与原裁决一致，不能修改 ready 标记绕过。
- 新审计按 research-runs 文件保存，不挤进单个月记录；检查记录仍是进度唯一来源。请求发出前先保存 started 占用，响应返回后原子更新当前输出。中断意图也计入已收集审计的预算；失败后上传现有产物，不能冒充完成。JSON 按解码字段扫描，既防止转义凭据漏检，也避免换行装饰器被误报为邮箱。
- 用户页、首页及目录使用同源状态。Git 准备失败或新快照尚无研究时，旧通过正文不能覆盖新状态。只通过机制阶段不会显示公告；正式 digest 仍须所有者确认。
