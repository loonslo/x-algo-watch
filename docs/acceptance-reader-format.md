# 线上用户版格式验收

日期：2026-10-22。用户明确要求：非技术读者优先，技术内容弱化；关键是让后续线上模型按固定格式起草和复核，而不是长期依赖人工重写。

## 实现边界

- 固定阅读顺序为 30 秒摘要、影响解读、折叠的技术分析、折叠的研究附录与检查历史。每页和目录提供“怎么读”入口。
- `research_schema()` 定义精确 JSON 协议，导出 `schemas/version-research-v2.json`，自动追加到起草与复核两个角色的系统提示。根对象及嵌套字段明确，reader 必填；线上状态只允许 unverified，标题与四问合计最多 420 字符。提示词与协议共同计算版本指纹。
- 程序检查字段、长度、术语、数字/名字/路径、证据编号及上线承诺；发布边界同样拒绝缺 reader 的新稿。第一次失败携错误自动纠错，第二次失败停止正文发布。复核可对 reader 提出问题，反馈修订后仍有分歧时，用户正文标为待修订，旧稿只作为审计材料。
- 由程序统一排版和生成证据链接。后续新版本没有 editorial 文件也能完整生成；不再把技术 summary 复制成页面开头的一句话。
- 原始源码变化、机制推断和线上状态分别展示。置信度只保留在技术分析，并明确不评价部署或流量效果。新用户筛选默认 false、默认值与线上状态、标签查询例外与最终删除条件分别说明。

## 已有研究迁移

9 份已有研究绑定原 research_id、item_id 进行一次阅读层迁移，其中 3 份旧分歧稿把问题落实到改写内容；原始调用审计、正式 digest 和人工登记均未更改。没有将本次改写冒充新的 MiniMax 复核或所有者确认。

最新版本额外只读核对 `989fb91` 的关系标记赋值及完整 Fair Share 实现，R1/R2 保存片段、提交、行号和摘要，与原模型 E 证据区分。确认按来源候选数量比例控制保留，不按账号大小分组；标签读取代码未给出完整 SOFT_NSFW 判定标准，不自行归类。

旧改写只有在绑定研究仍作为阅读来源时才会应用；新研究自动使用自身的 reader。额度不足产生待续写事件时，不清空此前已有研究和阅读稿。兼容清单只复用 6 份已同意的旧机制研究，未通过稿仍按新协议排队。44 份研究的队列没有被伪装成全部完成。

## 本地检查

Windows / Python 3.14.0，完整测试：**206 passed in 61.17s**，包含真实历史回放与 29 行迁移。读者格式、模型和发布相关一轮测试：**57 passed in 25.46s**。随后收紧新研究发布边界，相关结果在下文续录。

已验证的关键行为：

- 起草与复核实际收到的协议相同，导出 JSON 与程序定义一致。
- 不准备任何 editorial 文件的新版本，模拟模型起草、reader 分歧、反馈修订、复核通过、自动发布后具备四层结构，错误影响对象已从正文移除。
- 缺少 reader 的输出自动纠错一次；仍缺失则不进入可发布正文，伪造新研究产物也不能绕过发布校验。
- 新稿 reader 字段、证据、长度、术语或线上状态错误被拦；原始历史审计仍可读取。
- 旧阅读稿精确绑定研究，补充来源摘要篡改会拒绝；新研究不能沿用旧稿。
- 新版额度等待不会让旧阅读页退回空白；重建保持检查记录、登记表与正式速报不变。

实际补充片段与临时裸仓库中的 Git 对象逐行一致；原上游工作区不变。51 份版本档案及目录已重建，可点击的项目内链接检查通过；原始源码放在 pre 区的字面链接不当作页面链接。UTC 当日模型调用审计仍为 50，未调用真实模型、未读取密钥。
